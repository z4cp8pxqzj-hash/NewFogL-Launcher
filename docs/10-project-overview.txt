================================================================================
第一章  这个项目是什么
================================================================================

--------------------------------------------------------------------------------
1.1  一句话解释
--------------------------------------------------------------------------------

	NewFogL 是一个 Minecraft 1.20.1 的启动器。

	它的特殊之处在于：能让 Forge、NeoForge、Fabric 这三种加载器的 mod
	在同一个游戏里共存（当前版本未实现）。

	普通启动器：一个实例只能选一种加载器。
	NewFogL：一个实例可以同时装三种加载器的 mod（当前版本未实现）。


--------------------------------------------------------------------------------
1.2  为什么要做这个
--------------------------------------------------------------------------------

	Minecraft Java 版有三种主流 mod 加载器：

		· Forge：老牌加载器，工业类 mod 多
		· NeoForge：从 Forge 分家出来的新加载器
		· Fabric：轻量加载器，优化类 mod 多

	每种加载器都有自己的 mod 生态。玩家想同时玩工业 mod 和优化 mod，
	就得装两个实例、来回切换。

	NewFogL 的目标是：一个实例，三种 mod 都能装。


--------------------------------------------------------------------------------
1.3  它和 PCL2 有什么区别
--------------------------------------------------------------------------------

	PCL2 是一个通用的 MC 启动器，支持多个 MC 版本，但不支持三加载器共存。

	NewFogL 只做 1.20.1，只做三加载器共存这一件事，把这件事做到极致。

	打个比方：
		· PCL2 是"大超市"，什么都有
		· NewFogL 是"专营店"，只卖一样东西，但卖到最好


================================================================================
第二章  项目由哪些部分组成
================================================================================

--------------------------------------------------------------------------------
2.1  两大组件
--------------------------------------------------------------------------------

	NewFogL 由两个独立的程序组成：

		【启动器】NewFogL.exe
			· 用户看得见的界面
			· 负责：显示界面、管理实例、启动游戏
			· 用 C++ 写的（Qt6 Widgets 图形界面）

		【加载器】newfog-loader.jar
			· 用户看不见的后台程序
			· 负责：扫描 mod、检查冲突、部署文件
			· 用 Java 写的

	启动器"指挥"加载器干活，加载器"完成"具体任务。


--------------------------------------------------------------------------------
2.2  为什么分两个程序
--------------------------------------------------------------------------------

	因为两个程序擅长的事不一样：

		C++ 擅长：图形界面、文件操作、进程管理
		Java 擅长：处理 jar 文件、分析字节码、管理类加载

	如果强行用一种语言做全部，会做得很别扭。

	用两种语言，各司其职，才能把每件事都做到最好。


--------------------------------------------------------------------------------
2.3  用户看到的流程
--------------------------------------------------------------------------------

	用户双击 NewFogL.exe
		↓
	弹出启动器界面
		↓
	用户选择实例，点击"启动游戏"
		↓
	启动器叫醒"加载器"
		↓
	加载器扫描 mod、检查冲突、准备文件
		↓
	加载器叫醒"游戏"
		↓
	游戏启动，用户开始玩

第三章  目录结构入门
================================================================================

--------------------------------------------------------------------------------
3.1  顶层结构
--------------------------------------------------------------------------------

	在你安装 NewFogL 的目录下，会看到这样的结构：

		.minecraft\
		├── NewFogL.exe			启动器本体
		├── versions\				每个实例一个文件夹
		├── NewFogL\				启动器自己的数据
		├── libraries\			游戏依赖库
		├── assets\				游戏资源（音效、贴图）
		└── runtime\				Java 运行时


--------------------------------------------------------------------------------
3.2  什么是"实例"
--------------------------------------------------------------------------------

	"实例"是 NewFogL 的核心概念。

	一个实例 = 一套独立的游戏配置，包含：

		· 自己的 mod
		· 自己的存档
		· 自己的配置
		· 自己的资源包
		· 自己的光影

	实例之间完全隔离，互不干扰。

	你可以建三个实例：
		· "工业时代"：只装工业类 mod
		· "纯净生存"：只装优化类 mod
		· "光影测试"：专门测试光影


--------------------------------------------------------------------------------
3.3  为什么要版本隔离
--------------------------------------------------------------------------------

	因为不同的 mod 需要不同的环境。

	比如：
		· 工业 mod 会改游戏内核
		· 优化 mod 也会改游戏内核
		· 两者改的地方冲突，放一起就崩

	版本隔离就是"分家"：
		· 工业 mod 放工业实例
		· 优化 mod 放优化实例
		· 谁也不影响谁


--------------------------------------------------------------------------------
3.4  Junction 是什么
--------------------------------------------------------------------------------

	Junction 是 Windows 的一种"目录快捷方式"。

	打个比方：
		· 你的存档实际上在 A 文件夹
		· 但游戏认为存档在 B 文件夹
		· B 文件夹是一个 Junction，指向 A
		· 游戏往 B 里写文件，实际写到了 A

	为什么要这么做？

	因为 NewFogL 想让所有实例的数据集中管理（在 NewFogL\cache\ 下），
	但游戏只认自己目录下的文件夹（versions\{实例名}\ 下）。

	Junction 让两边都能满足。

第四章  启动流程入门
================================================================================

--------------------------------------------------------------------------------
4.1  启动游戏的完整流程
--------------------------------------------------------------------------------

	用户点击"启动游戏"
		↓
	【第1步】加载器扫描 mod 文件夹
		→ 看里面有哪些 mod
		↓
	【第2步】加载器分析每个 mod 的信息
		→ 这个 mod 叫什么、属于哪个加载器、依赖什么
		↓
	【第3步】加载器检查冲突
		→ 有没有重复的 mod、有没有缺依赖、有没有违规的
		↓
	【第4步】加载器决定加载顺序
		→ 谁先加载、谁后加载
		↓
	【第5步】加载器准备部署文件
		→ 把 mod 重命名、复制到游戏能读的地方
		↓
	【第6步】加载器生成启动脚本
		→ 写一个 .bat 文件，里面是启动游戏的命令
		↓
	【第7步】加载器启动游戏
		→ 运行那个 .bat 文件，游戏就起来了


--------------------------------------------------------------------------------
4.2  为什么要有"检查冲突"这一步
--------------------------------------------------------------------------------

	mod 冲突是常见问题。比如：

		· 同一个 mod 装了两个版本
		· Forge 的 mod 和 Fabric 的 mod 混在一起
		· 某个 mod 缺少前置 mod

	如果不检查，游戏启动时就会崩溃，而且崩溃信息很难看懂。

	NewFogL 的"检查冲突"就是：在游戏启动之前，先发现这些问题，
	然后告诉用户"你这里有问题，请先解决"。


--------------------------------------------------------------------------------
4.3  五道红线是什么
--------------------------------------------------------------------------------

	“五道红线”是五种必须拦截的冲突：

		1. 多版本：同一个 mod 装了两个版本
		2. 缝合怪：Forge 的 mod 依赖 Fabric 的东西
		3. 依赖缺失：某个 mod 需要的前置没装
		4. 套壳模组：两个 mod 功能几乎一样（比如 Sodium 和 Rubidium）
		5. 跨加载器重复：同一个 mod 同时装在了 Forge 和 Fabric 里

	只要触发任意一条，启动就会中止，并弹出提示告诉用户问题在哪（弹窗当前版本未实现，仅日志中止）。

================================================================================
第六章  开发入门
================================================================================

--------------------------------------------------------------------------------
6.1  开发环境需要什么
--------------------------------------------------------------------------------

	开发 Java 加载器：
		· JDK 21
		· IntelliJ IDEA（推荐）或 Eclipse
		· Gradle（项目自带 Wrapper）

	开发 C++ 启动器：
		· Visual Studio 2022（包含 MSVC）
		· CMake 3.20 以上
		· Qt 6（Widgets 组件）
		· Git

	其他：
		· 一个文本编辑器（推荐 VS Code）
		· 一个 AI 助手（ChatGPT、Claude、Cursor 等）


--------------------------------------------------------------------------------
6.2  开发顺序
--------------------------------------------------------------------------------

	先做加载器，再做启动器。

	为什么？
		· 加载器是核心，负责所有关键逻辑
		· 加载器可以独立测试（命令行运行）
		· 启动器只是外壳，加载器做好了，外壳很简单

	如果先做启动器，会卡在"没有加载器可调"这一步。


--------------------------------------------------------------------------------
6.3  用 AI 开发的正确姿势
--------------------------------------------------------------------------------

	【做】：
		· 让 AI 按文档实现单个文件
		· 每次只让 AI 写一个文件
		· 写完验收，符合文档才继续
		· 遇到问题定位根因，不绕过

	【不做】：
		· 一次性让 AI 写整个项目
		· 让 AI 自由发挥
		· 不验收就继续下一个
		· 让 AI "优化"文档里的设计


--------------------------------------------------------------------------------
6.4  遇到报错怎么办
--------------------------------------------------------------------------------

	第1步：仔细读报错信息，找到出错的文件和行号

	第2步：看报错信息里的关键词（比如 NullPointerException、找不到类）

	第3步：对照文档，看这块是不是偏离了设计

	第4步：如果自己看不懂，把报错信息 + 相关代码 + 文档章节发给 AI

	第5步：AI 给方案后，不要直接粘贴，先理解再改

	重点：报错不可怕，可怕的是不看报错就乱改。


================================================================================
第七章  常见问题
================================================================================

--------------------------------------------------------------------------------
7.1  为什么不直接做一个加载器
--------------------------------------------------------------------------------

	因为三大加载器（Forge、NeoForge、Fabric）的设计哲学完全不同。

	硬要做成一个，最后会做成一个四不像：
		· 兼容性差
		· 维护困难
		· 出了问题没人能修

	NewFogL 的思路是：不合并加载器，而是让它们共存（当前版本未实现）。

	具体来说：
		· 每个加载器在自己的"沙盒"里跑
		· 沙盒之间互不干扰
		· 由一个"总控制器"负责协调


--------------------------------------------------------------------------------
7.2  为什么只支持 1.20.1
--------------------------------------------------------------------------------

	因为 1.20.1 是目前 mod 生态最活跃的版本：
		· Forge 47.x 是最成熟的版本
		· Fabric 生态完整
		· NeoForge 也支持

	支持一个版本，可以把这个版本做到极致。

	支持多个版本，会陷入"每个版本都要维护"的泥潭。


--------------------------------------------------------------------------------
7.3  为什么不用 Python 或 C#
--------------------------------------------------------------------------------

	因为：
		· Java 是 Minecraft 的原生语言，处理 jar 最方便
		· C++ 适合做 Windows 原生程序，性能和体积都好

	Python 太慢，C# 依赖 .NET 运行时。


--------------------------------------------------------------------------------
7.4  为什么 exe 有 150 多 MB 这么大
--------------------------------------------------------------------------------

	因为里面塞了很多东西：
		· Java 17 运行时（约 65 MB 压缩后）
		· Java 21 运行时（约 72 MB 压缩后）
		· 三个加载器的安装包（约 20 MB）
		· 启动器自己的代码和资源

	打包后大约 157-172 MB（Minecraft 核心不内嵌，见下）。

	为什么 Java 和加载器内嵌，Minecraft 核心却从官方源下载？
		· JRE 和加载器体积大、来源分散，内嵌 = 开箱即用，用户双击就能跑
		· Minecraft 核心是官方文件，官方源提供带 SHA1 的下载地址，
		  从官方源拉取能保证文件完整、可随版本更新，也避免二次分发
		· 代价：首次创建实例/首次启动需要联网；本地已有核心时直接复用


================================================================================
第八章  给新人的建议
================================================================================

--------------------------------------------------------------------------------
8.1  不要急着写代码
--------------------------------------------------------------------------------

	先读文档，理解：
		· 项目要解决什么问题
		· 由哪些部分组成
		· 每部分负责什么
		· 部分之间怎么配合

	读懂了再动手，能省下大量返工时间。


--------------------------------------------------------------------------------
8.2  不要一开始就追求完美
--------------------------------------------------------------------------------

	第一版能跑通核心流程就行：
		· 能创建实例
		· 能扫描 mod
		· 能检查冲突
		· 能启动游戏

	其他功能（导出整合包、UI 美化、多语言）都可以后续再加。

	完美是完成之敌。


--------------------------------------------------------------------------------
8.3  每次改动都要小步前进
--------------------------------------------------------------------------------

	不要一次改很多地方：
		· 改一个文件 → 测试 → 通过 → 下一个
		· 改一个功能 → 测试 → 通过 → 下一个

	如果一次改很多，出错了不知道是哪一处引起的。


--------------------------------------------------------------------------------
8.4  保留好每个能跑的版本
--------------------------------------------------------------------------------

	用 Git 管理代码：
		· 每完成一个模块，提交一次
		· 提交信息写清楚改了什么
		· 出问题可以回退到上一个能跑的版本

	不要等到项目做完才提交，那时候已经晚了。


--------------------------------------------------------------------------------
8.5  遇到不懂的名词，先查再问
--------------------------------------------------------------------------------

	常见名词：
		· 类加载器（ClassLoader）：Java 里负责加载类的组件
		· 沙盒（Sandbox）：隔离环境，一个沙盒里的东西不影响另一个
		· 拓扑排序：根据依赖关系排出一个先后顺序
		· Junction：Windows 的目录快捷方式
		· 硬链接：两个文件名指向同一份文件数据

	不懂的查一下，比直接问效率高。

9.1  启动器（C++ / Qt6）
--------------------------------------------------------------------------------

	已完成：Qt6 Widgets 图形界面（无边框窗口、主窗口、侧边栏、日志面板、
	版本选择页、实例设置页，以及按钮／列表／开关／对话框等控件）。

	崩溃弹窗（CrashDialog）尚未实现，崩溃仅由 CrashDetector /
	CrashAnalyzer 记录与分析。

	未纳入编译：ui/InstanceSelectPage、src/main-cmd.cpp（保留备用）。


--------------------------------------------------------------------------------
9.2  加载器（Java / newfog-loader）
--------------------------------------------------------------------------------

	newfog-loader 共 42 个 .java 源文件，分 8 个包（另加入口 Main.java）：

		model(6)      LoaderTag / Dependency / ModDescriptor /
		              ModIdentifier / DeployManifest / ArbitrationRules
		log(4)        NewFogLogger / LogLevel / LogModule / LogRotator
		scanner(6)    MetadataScanner / LoaderDetector / FabricParser /
		              ForgeParser / NeoForgeParser / ForbiddenCompatChecker
		preflight(7)  PreFlightChecker / MultiVersionChecker / CrossLoaderChecker /
		              DependencyChecker / SkinModChecker / DuplicateChecker /
		              FatalArbitrationError（五道红线）
		resolver(5)   DependencyGraph / TopologicalSorter / TarjanSCC /
		              CycleGroupResolver / LoaderPrioritySorter
		deploy(5)     FingerprintGenerator / CacheValidator / FileLinker /
		              ModDeployer / DeployManifestWriter
		sandbox(3)    SandboxPlanner / SharedLibraryResolver /
		              NewFogSandboxClassLoader
		launcher(5)   LaunchPlanWriter / ScriptGenerator / JvmArgsBuilder /
		              GameProcessLauncher / GameOptionsInitializer

	Main.java 实际阶段顺序：扫描 → 短编号 → 静态预检 → 依赖解析 →
	加载器优先级 → 沙盒规划 → 指纹／缓存校验 → 部署 → 生成脚本 → 拉起进程。


--------------------------------------------------------------------------------
9.3  尚未实现
