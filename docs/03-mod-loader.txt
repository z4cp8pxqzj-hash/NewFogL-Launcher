================================================================================
第一部分  模块概述
================================================================================

New Fog 加载器是 NewFogL 启动器的核心引擎，由 C++ 启动器以独立进程调用。

职责范围：

	· 扫描 mod 源目录，解析元数据，判定加载器归属
	· 执行五道红线静态预检
	· 构建依赖图，拓扑排序，处理循环依赖
	· 部署模组到部署区，按规则重命名
	· 规划沙盒，隔离三大加载器
		· 生成游戏启动脚本
	· 拉起 Java 17 游戏进程
	· 输出日志和状态回传

不负责：

	· UI 界面
	· 进程守护
	· 崩溃检测
	· 导出/导入整合包
	· Junction 创建（由启动器负责）
	· 内嵌资源释放（由启动器负责）

第二部分  Java 版本分工
================================================================================

进程						Java 版本	用途
------------------------	----------	--------------------------------
NewFogL.exe (C++)			—			启动器 UI 与进程管理
newfog-loader.jar			Java 21		扫描/预检/部署/沙盒规划
游戏进程						Java 17		运行 Minecraft 1.20.1


调用链：

	NewFogL.exe
		│
		│ 使用 jre-21 拉起加载器
		▼
	java.exe (jre-21) -jar newfog-loader.jar --instance ...
		│
		│ 加载器执行完预检/部署后，使用 jre-17 拉起游戏
		▼
	java.exe (jre-17) net.minecraft.client.main.Main --gameDir ...


关键约束：

	· 加载器自身运行在 Java 21 上
	· 加载器通过 ProcessBuilder 拉起游戏进程
	· 游戏进程使用 Java 17
	· 两个 Java 版本内嵌在 exe 中，运行时释放到 .minecraft\runtime\

================================================================================
第六部分  扫描器
================================================================================

--------------------------------------------------------------------------------
6.1  MetadataScanner（元数据扫描器）
--------------------------------------------------------------------------------

入口方法：

	scan(Path modsDir) → List<ModDescriptor>

流程：

	1. 递归遍历 modsDir 下所有文件
	2. 过滤 .jar 后缀，排除 .disabled
	3. 对每个 jar：
		a. 打开 ZipFile
		b. 调用 LoaderDetector 判定加载器归属
		c. 调用对应的 Parser 解析元数据
		d. 封装为 ModDescriptor
	4. 返回结果列表

异常处理：

	· ZipFile 打不开 → 记录 WARN，跳过该文件
	· 元数据解析失败 → 记录 WARN，标记为 UNKNOWN
	· 读取权限不足 → 记录 ERROR，抛出异常

日志输出：

	[INFO] [Scanner] 开始扫描: {modsDir}
	[INFO] [Scanner] 发现 {n} 个 jar 文件
	[DEBUG] [Scanner] 解析: {jarFileName} → modid={modId}
	[INFO] [Scanner] 解析完成，{n} 个 ModDescriptor


--------------------------------------------------------------------------------
6.2  LoaderDetector（加载器判定）
--------------------------------------------------------------------------------

判定优先级（严格顺序）：

	1. 存在 META-INF/neoforge.mods.toml → NEOFORGE
	2. 存在 fabric.mod.json → FABRIC
	3. 存在 META-INF/mods.toml → 二次判定：
		a. 文件内容含 "neoforge" → NEOFORGE
		b. 否则 → FORGE
	4. 无任何元数据 → UNKNOWN

伪代码：

	LoaderTag detect(Path jarPath) {
		ZipFile zip = openZip(jarPath);
		if (zip.contains("META-INF/neoforge.mods.toml")) {
			return NEOFORGE;
		}
		if (zip.contains("fabric.mod.json")) {
			return FABRIC;
		}
		if (zip.contains("META-INF/mods.toml")) {
			String content = readEntry(zip, "META-INF/mods.toml");
			if (content.contains("neoforge")) return NEOFORGE;
			return FORGE;
		}
		return UNKNOWN;
	}


--------------------------------------------------------------------------------
6.3  FabricParser（Fabric 元数据解析器）
--------------------------------------------------------------------------------

解析文件：fabric.mod.json

提取字段：

	· id			→ modId
	· version		→ version
	· name			→ displayName
	· depends		→ hardDeps
	· recommends	→ softDeps
	· conflicts		→ conflicts

依赖格式：

	JSON 对象，key 为 modId，value 为版本范围字符串
	如："fabric-api": ">=0.92.0"

示例：

	{
		"id": "sodium",
		"version": "0.5.8",
		"name": "Sodium",
		"depends": {
			"fabricloader": ">=0.15.0",
			"fabric-api": "*",
			"minecraft": "1.20.1"
		}
	}


--------------------------------------------------------------------------------
6.4  ForgeParser / NeoForgeParser
--------------------------------------------------------------------------------

解析文件：META-INF/mods.toml 或 META-INF/neoforge.mods.toml

提取字段：

	· modId			→ modId
	· version		→ version
	· displayName	→ displayName
	· dependencies	→ hardDeps / softDeps
	· 读取 META-INF/jarjar/ 下的嵌套 jar，提取其 modId

依赖格式：

	[[dependencies.xxx]]
		modId = "forge"
		mandatory = true
		versionRange = "[47.0.0,)"
		ordering = "NONE"
		side = "BOTH"

	mandatory = true  → hardDeps
	mandatory = false → softDeps
	side = SERVER     → 忽略（只做客户端）

示例：

	modLoader = "javafml"
	loaderVersion = "[47,)"
	license = "LGPL"

	[[mods]]
		modId = "jei"
		version = "15.2.0"
		displayName = "Just Enough Items"

	[[dependencies.jei]]
		modId = "forge"
		mandatory = true
		versionRange = "[47.0.0,)"
		ordering = "NONE"
		side = "BOTH"


--------------------------------------------------------------------------------
6.5  ForbiddenCompatChecker（缝合怪检测）
--------------------------------------------------------------------------------

规则：

	· Forge / NeoForge 的模组，依赖列表含 fabric-api / fabric / fabricloader → 拦截
	· LoaderTag.FABRIC 的模组，依赖列表含 forge / neoforge → 拦截
	· 依赖列表含 sinytra_connector / forgified-fabric-api → 拦截

输出：

	FatalArbitrationError("CrossLoader", 详细信息, 涉及模组列表)

日志示例：

	[ERROR] [Scanner] CrossLoader: 模组 xxx 是 FORGE 模组，但依赖 fabric-api
	[ERROR] [Scanner] 涉及模组: xxx-forge-1.0.jar

第七部分  静态预检
================================================================================

--------------------------------------------------------------------------------
7.1  PreFlightChecker（主预检器）
--------------------------------------------------------------------------------

入口方法：

	check(List<ModDescriptor> mods) → PreFlightResult

执行顺序（五道红线，顺序不能变）：

	1. MultiVersionChecker
	2. CrossLoaderChecker
	3. DependencyChecker
	4. SkinModChecker
	5. DuplicateChecker

任一道触发 → 抛出 FatalArbitrationError，中止预检

日志输出：

	[INFO] [PreFlight] 开始静态预检
	[INFO] [PreFlight] 多版本拦截: 通过
	[INFO] [PreFlight] 缝合怪拦截: 通过
	[INFO] [PreFlight] 依赖模糊拦截: 通过
	[INFO] [PreFlight] 套壳模组拦截: 通过
	[INFO] [PreFlight] 跨加载器重复拦截: 通过
	[INFO] [PreFlight] 静态预检通过


--------------------------------------------------------------------------------
7.2  红线1：MultiVersionChecker（多版本拦截）
--------------------------------------------------------------------------------

触发条件：

	同一加载器下，同 modid 出现多个版本

检测逻辑：

	Map<String, List<ModDescriptor>> groupByLoaderAndModId;
	for (ModDescriptor mod : allMods) {
		String key = mod.getLoaderType() + ":" + mod.getModId();
		groupByLoaderAndModId.computeIfAbsent(key, k -> new ArrayList<>())
							  .add(mod);
	}
	for (entry : groupByLoaderAndModId) {
		if (entry.getValue().size() > 1) {
			throw FatalArbitrationError;
		}
	}

弹窗标题：检测到多版本模组

弹窗内容：

	模组 {modid} 存在多个版本：
	- sodium-0.5.8.jar
	- sodium-0.6.0.jar
	请移除多余版本后重试。

日志示例：

	[ERROR] [PreFlight] MultiVersion: sodium 存在多个版本
	[ERROR] [PreFlight] 涉及模组: sodium-0.5.8.jar, sodium-0.6.0.jar


--------------------------------------------------------------------------------
7.3  红线2：CrossLoaderChecker（缝合怪拦截）
--------------------------------------------------------------------------------

触发条件：

	Forge 模组依赖 Fabric API，或反之

检测逻辑：

	· loaderType == FORGE 且依赖列表含 fabric-api → 拦截
	· loaderType == FABRIC 且依赖列表含 forge / neoforge → 拦截
	· 依赖列表含 sinytra_connector / forgified-fabric-api → 拦截

弹窗标题：检测到违禁的跨加载器兼容层

弹窗内容：

	模组 {filename} 是 {loader} 模组，但依赖了 {otherLoader} API。
	NewFogL 严禁此类缝合模组，请移除。

日志示例：

	[ERROR] [PreFlight] CrossLoader: 模组 xxx 是 FORGE 模组，但依赖 fabric-api
	[ERROR] [PreFlight] 涉及模组: xxx-forge-1.0.jar


--------------------------------------------------------------------------------
7.4  红线3：DependencyChecker（依赖模糊拦截）
--------------------------------------------------------------------------------

触发条件：

	· loaderType == UNKNOWN（无法判定加载器归属）
	· 元数据解析失败
	· 缺少硬依赖
	· 硬依赖版本范围不匹配

检测逻辑：

	对每个 mod 的 hardDeps：
		查找本地是否有对应 modId
		不存在 → 拦截
		存在但版本不匹配 → 拦截
	跳过规则：
		· 当前 mod 的硬依赖，如果在自己或其他 mod 的 bundledModIds 里 → 跳过
		· modId 以 "fabric-" 开头的，视作 Fabric API 子模块 → 跳过

弹窗标题：依赖解析失败

弹窗内容：

	模组 {modid} 依赖 {depId} 版本 {versionRange}，
	但本地未找到匹配版本。
	请安装对应依赖后重试。

日志示例：

	[ERROR] [PreFlight] DependencyMissing: create 需要 flywheel >= 0.6.0
	[ERROR] [PreFlight] 涉及模组: create-1.20.1-0.5.1.f.jar


--------------------------------------------------------------------------------
7.5  红线4：SkinModChecker（套壳模组拦截）
--------------------------------------------------------------------------------

触发条件：

	字节码相似度 > 85% 且 modId 不同（仅同加载器内比较）

检测逻辑：

	1. 提取每个 jar 里所有 .class 文件的 SHA-256 集合
	2. 计算两两之间的 Jaccard 相似度：
		相似度 = |A ∩ B| / |A ∪ B|
	3. 相似度 > 0.85 且 modId 不同 → 拦截

缓存优化：

	· 首次扫描时计算特征码，写入缓存
	· 后续启动只对新增/修改的 jar 重算
	· 缓存文件：{cacheDir}/skinmod-cache.txt（缓存键：jar 文件大小_修改时间）

弹窗标题：检测到套壳模组

弹窗内容：

	{modA} 和 {modB} 的字节码相似度达 {percent}%，功能高度重叠。
	请保留其中一个。

日志示例：

	[WARN] [PreFlight] FakeMod: sodium 和 rubidium 字节码相似度 92%
	[WARN] [PreFlight] 涉及模组: sodium-0.5.8.jar, rubidium-0.6.0.jar


--------------------------------------------------------------------------------
7.6  红线5：DuplicateChecker（跨加载器重复拦截）
--------------------------------------------------------------------------------

触发条件：

	同一 modid 出现在多个加载器中

检测逻辑：

	Map<String, Set<LoaderTag>> modIdToLoaders;
	for (ModDescriptor mod : allMods) {
		modIdToLoaders.computeIfAbsent(mod.getModId(), k -> new HashSet<>())
					  .add(mod.getLoaderType());
	}
	for (entry : modIdToLoaders) {
		if (entry.getValue().size() > 1) {
			throw FatalArbitrationError;
		}
	}

白名单（跳过检查）：

	forge, neoforge, fabricloader, fabric-api, fabric,
	minecraft, java, mcp, mixin, architectury, cloth-config

弹窗标题：同一模组存在于多个加载器

弹窗内容：

	模组 {modid} 同时存在于多个加载器中：
	- FORGE: sodium-forge-0.5.8.jar
	- FABRIC: sodium-fabric-0.5.8.jar
	请保留其中一个加载器的版本。

日志示例：

	[ERROR] [PreFlight] CrossDuplicate: sodium 同时存在于 FORGE 和 FABRIC
	[ERROR] [PreFlight] 涉及模组: sodium-forge-0.5.8.jar, sodium-fabric-0.5.8.jar


--------------------------------------------------------------------------------
7.7  FatalArbitrationError（统一异常）
--------------------------------------------------------------------------------

字段：

	· redLine		字符串			红线名称
	· affectedMods	列表<字符串>	涉及的模组
	· userMessage	字符串			用户可见的提示
	· logMessage	字符串			日志记录的消息

构造方法：

	FatalArbitrationError(
		String redLine,
		String userMessage,
		List<String> affectedMods
	)

抛出行为：

	· 写入 ERROR 日志
	· 写入 [STATE] ABORT <原因>
	· 设置退出码为 1
	· 立即中止启动


================================================================================
第八部分  依赖解析
================================================================================

--------------------------------------------------------------------------------
8.1  DependencyGraph（依赖图）
--------------------------------------------------------------------------------

节点：所有 ModDescriptor（用短编号标识）
边：如果 A 硬依赖 B，则添加边 B → A（B 必须先加载）

只考虑硬依赖，软依赖不参与拓扑排序。

数据结构：

	class DependencyGraph {
		Map<String, Set<String>> adjacency;    // 节点 → 后继
		Map<String, Integer> inDegree;         // 节点 → 入度
		
		void addNode(String shortId);
		void addEdge(String from, String to);
		Set<String> getSuccessors(String node);
		Set<String> getAllNodes();
		int getInDegree(String node);
		void decreaseInDegree(String node);
	}

构建流程：

	for (ModDescriptor mod : allMods) {
		graph.addNode(mod.getShortId());
		for (Dependency dep : mod.getHardDeps()) {
			ModDescriptor depMod = findModByModId(dep.getModId());
			if (depMod != null) {
				graph.addEdge(depMod.getShortId(), mod.getShortId());
			}
		}
	}


--------------------------------------------------------------------------------
8.2  TopologicalSorter（拓扑排序）
--------------------------------------------------------------------------------

算法：Kahn 算法（基于入度的 BFS）

流程：

	1. 遍历所有节点，把入度为 0 的节点入队
	2. 依次出队：加入结果列表，对其每个后继的入度减 1
	3. 后继入度变为 0 时入队
	4. 重复直到队列为空
	5. 结果数量 < 节点总数 → hasCycle = true，交由 TarjanSCC 处理

入口方法：

	sort(DependencyGraph graph) → Result

Result 结构：

	class Result {
		List<String> sorted;    // 排序后的短编号有序列表
		boolean hasCycle;       // 是否存在环
	}

伪代码：

	public static Result sort(DependencyGraph graph) {
		List<String> result = new ArrayList<>();
		Queue<String> queue = new LinkedList<>();

		// 1. 所有入度为 0 的节点先入队
		for (String node : graph.getAllNodes()) {
			if (graph.getInDegree(node) == 0) {
				queue.offer(node);
			}
		}

		// 2. BFS 遍历
		while (!queue.isEmpty()) {
			String current = queue.poll();
			result.add(current);

			for (String next : graph.getSuccessors(current)) {
				graph.decreaseInDegree(next);
				if (graph.getInDegree(next) == 0) {
					queue.offer(next);
				}
			}
		}

		// 3. 结果数量 < 节点总数 → 有环
		boolean hasCycle = result.size() != graph.size();
		return new Result(result, hasCycle);
	}

说明：

	· 本方法不再抛 CircularDependencyException，而是通过 Result.hasCycle 返回"是否有环"
	· 是否进入 TarjanSCC 由调用方（Main 阶段4）依据 hasCycle 决定，不在本类内处理

日志输出：

	[INFO] [Resolver] 构建依赖图，共 {n} 个节点
	[INFO] [Resolver] 拓扑排序完成，共 {n} 个节点


--------------------------------------------------------------------------------
8.3  TarjanSCC（强连通分量）
--------------------------------------------------------------------------------

用途：识别循环依赖组

算法：Tarjan 强连通分量

流程：

	index = 0
	stack = []
	for each node in graph:
		if node.index is undefined:
			strongConnect(node)
	
	function strongConnect(v):
		v.index = index
		v.lowlink = index
		index++
		stack.push(v)
		v.onStack = true
		
		for each w in v.successors:
			if w.index is undefined:
				strongConnect(w)
				v.lowlink = min(v.lowlink, w.lowlink)
			else if w.onStack:
				v.lowlink = min(v.lowlink, w.index)
		
		if v.lowlink == v.index:
			component = []
			repeat:
				w = stack.pop()
				w.onStack = false
				component.add(w)
			until w == v
			if component.size > 1:
				cycleGroups.add(component)

输出：List<List<String>>（环组列表）

日志输出：

	[INFO] [Resolver] 检测到 {n} 个循环依赖组
	[INFO] [Resolver] 环组 [CG-001] 包含: F-001, B-005

	String generate(List<ModDescriptor> mods) {

	}

12.3  GameProcessLauncher（游戏进程拉起）
--------------------------------------------------------------------------------

重要：游戏进程使用 Java 17，不是 Java 21。

		· javaPath 指向 runtime\jre-17\bin\java.exe
	2. 构造 ProcessBuilder：

		· 工作目录：versions\{实例名}\
	3. 重定向 stdout/stderr
	4. 启动进程
	5. 等待进程退出
	6. 读取退出码
	7. 将退出码返回给 C++ 启动器

	· 游戏进程退出码
	· 最后 100 行游戏日志（可选）

	· 加载器本身运行在 Java 21
	· 加载器通过 ProcessBuilder 拉起 Java 17 的游戏进程
	· 两个 JVM 是父子进程关系
	· 加载器退出前，游戏进程必须结束（或加载器不等游戏结束直接退出）

日志输出：

	[INFO] [Launcher] 游戏进程已启动，PID: {pid}
	[INFO] [Launcher] 游戏进程退出，退出码: {code}

12.4  进程树
--------------------------------------------------------------------------------

	NewFogL.exe (C++)
		│
		└── java.exe (jre-21)  ← 加载器
				│
				└── java.exe (jre-17)  ← 游戏


	说明：
	· 加载器完成预检/部署后，可以：
		方案A：直接拉起游戏进程，等待游戏结束，然后把退出码返回给启动器
		方案B：只生成启动脚本，立即退出，由启动器执行脚本
	· 推荐方案A：加载器全程负责，启动器只需读取加载器退出码
	· 方案A下加载器进程会持续存在，直到游戏退出
