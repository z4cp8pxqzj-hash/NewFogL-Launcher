================================================================================
NewFogL 代码注释原则
================================================================================

文档版本：1.1.0
适用范围：C++ 启动器（NewFogL）+ Java 加载器（newfog-loader）
目的：让每个接手代码的人（包括未来的你自己、AI、其他贡献者）
	  能在不看完整实现的情况下，理解一段代码的职责、依据和边界


================================================================================
第一部分  总原则
================================================================================

--------------------------------------------------------------------------------
1.1  注释的目的是什么
--------------------------------------------------------------------------------

注释不解释"代码在做什么"，代码本身已经说明了。
注释解释"为什么这么做"和"依据在哪"。

	反例：
		// i 加 1
		i++;

	正例：
		// 短编号从 1 开始，0 保留给未知模组
		i++;

--------------------------------------------------------------------------------
1.2  注释的三个层级
--------------------------------------------------------------------------------

	层级1：文件头注释			—— 每个文件必须有
	层级2：类头 / 函数头注释	—— 每个类和公开方法必须有
	层级3：复杂逻辑块注释		—— 每个非显而易见的判断必须有

	不需要注释的地方：
		· getter / setter
		· 简单的构造方法
		· 一行的 if 判断
		· 自解释的变量名和方法名

--------------------------------------------------------------------------------
1.3  注释必须包含"文档依据"
--------------------------------------------------------------------------------

这是 NewFogL 项目特有的要求。

每段实现逻辑，都必须能追溯回开发文档的某一节。
如果追溯不到，说明这段实现可能偏离了设计。

	格式：
		// 文档依据：mod加载器开发文档 6.2
		// 文档依据：启动器开发文档 7.1
		// 文档依据：接口文档 3.2

	这条注释的意义：
		· 让后续维护者知道这段代码的设计初衷
		· 让文档和代码可以互相校验
		· 当你发现代码和文档不一致时，能定位到是哪一方写错了

第二部分  文件头注释
================================================================================

--------------------------------------------------------------------------------
2.1  Java 文件头模板
--------------------------------------------------------------------------------

	/**
	 * {类名} - {一句话职责}
	 *
	 * 文档依据：{文档名} {章节}
	 *
	 * 职责：
	 *   · {职责1}
	 *   · {职责2}
	 *
	 * 不负责：
	 *   · {明确排除的职责1}
	 *   · {明确排除的职责2}
	 *
	 * 依赖：
	 *   · {上游模块} - {依赖原因}
	 *
	 * 被依赖：
	 *   · {下游模块} - {被调用原因}
	 *
	 * @author NewFogL
	 * @since 1.0.0
	 */

	示例（LoaderDetector.java）：

	/**
	 * LoaderDetector - 加载器归属判定器
	 *
	 * 文档依据：mod加载器开发文档 6.2
	 *
	 * 职责：
	 *   · 判断一个 jar 属于 FORGE / NEOFORGE / FABRIC 中的哪一个
	 *   · 无法判定时返回 UNKNOWN
	 *
	 * 不负责：
	 *   · 打开 jar 文件（由调用方负责）
	 *   · 解析元数据内容（由 Parser 负责）
	 *   · 处理判定失败的业务逻辑（由 PreFlightChecker 负责）
	 *
	 * 依赖：
	 *   · LoaderTag - 返回值类型
	 *
	 * 被依赖：
	 *   · MetadataScanner - 扫描每个 jar 时调用 detect()
	 *
	 * @author NewFogL
	 * @since 1.0.0
	 */

2.2  C++ 文件头模板
--------------------------------------------------------------------------------

	/**
	 * {文件名} - {一句话职责}
	 *
	 * 文档依据：{文档名} {章节}
	 *
	 * 职责：
	 *   · {职责1}
	 *   · {职责2}
	 *
	 * 不负责：
	 *   · {明确排除的职责1}

--------------------------------------------------------------------------------
4.1  Java 方法头模板
--------------------------------------------------------------------------------

	/**
	 * {一句话说明这个方法做什么}
	 *
	 * 文档依据：{文档名} {章节}
	 *
	 * @param {参数名} {参数含义}
	 * @return {返回值含义}
	 * @throws {异常类型} {抛出条件}
	 */
	public LoaderTag detect(JarFile jar) {
		...
	}


--------------------------------------------------------------------------------
4.2  需要 @throws 标注的场景
--------------------------------------------------------------------------------

	如果方法内部可能抛出 FatalArbitrationError，
	必须在 @throws 里说明触发条件。

	示例：

	/**
	 * 执行五道红线静态预检
	 *
	 * 文档依据：mod加载器开发文档 7.1
	 *
	 * @param mods 所有已解析的模组
	 * @return 预检结果
	 * @throws FatalArbitrationError 任意一条红线触发时抛出
	 */
	public PreFlightResult check(List<ModDescriptor> mods) {
		...
	}


--------------------------------------------------------------------------------
4.3  不需要注释的方法
--------------------------------------------------------------------------------

	· getter / setter
	· 简单的构造方法
	· 重写的 equals / hashCode / toString
	· 一行就能看懂的委托方法

	示例（不加注释）：

	public String getShortId() {
		return shortId;
	}


--------------------------------------------------------------------------------
4.4  C++ 函数头模板
--------------------------------------------------------------------------------

	/**
	 * {一句话说明}
	 *
	 * 文档依据：{文档名} {章节}
	 *
	 * @param {参数名} {参数含义}
	 * @return {返回值含义}
	 *
	 * 注意事项：
	 *   · {调用方需要注意的事项}
	 */
	bool createJunction(const std::string& target,
						const std::string& source);


================================================================================
第五部分  复杂逻辑块注释
================================================================================

--------------------------------------------------------------------------------
5.1  什么算"复杂逻辑块"
--------------------------------------------------------------------------------

	· 非显而易见的判断条件
	· 硬编码的常量
	· 绕过某个已知问题的代码
	· 顺序敏感的逻辑
	· 有边界条件的循环

--------------------------------------------------------------------------------
5.2  判断条件注释
--------------------------------------------------------------------------------

	// 文档依据：mod加载器开发文档 6.2
	// neoforge.mods.toml 优先级最高，存在则直接判定为 NEOFORGE
	if (jar.contains("META-INF/neoforge.mods.toml")) {
		return LoaderTag.NEOFORGE;
	}


--------------------------------------------------------------------------------
5.3  硬编码常量注释
--------------------------------------------------------------------------------

	// 短编号格式：{首字母}-{三位数字}
	// 首字母：F=Forge, N=NeoForge, B=Fabric
	// 文档依据：mod加载器开发文档 5.4
	String shortId = String.format("%s-%03d", prefix, count);


--------------------------------------------------------------------------------
5.4  绕过已知问题注释
--------------------------------------------------------------------------------

	// 文档依据：mod加载器开发文档 9.4
	// Windows 跨盘符时硬链接会失败，降级为复制
	// 检测方式：比较源路径和目标路径的盘符
	if (!sourceRoot.equals(targetRoot)) {
		Files.copy(source, target, StandardCopyOption.REPLACE_EXISTING);
	}


--------------------------------------------------------------------------------
5.5  顺序敏感逻辑注释
--------------------------------------------------------------------------------

	// 文档依据：mod加载器开发文档 7.1
	// 五道红线必须按此顺序执行：
	// 1. MultiVersionChecker 先拦截多版本，避免后续判定出现歧义
	// 2. CrossLoaderChecker 次之，避免缝合怪进入依赖解析
	// 3. DependencyChecker 依赖前两步的结果
	// ...
	checkMultiVersion(mods);
	checkCrossLoader(mods);
	checkDependency(mods);
	checkSkinMod(mods);
	checkDuplicate(mods);


--------------------------------------------------------------------------------
5.6  边界条件注释
--------------------------------------------------------------------------------

	// 文档依据：mod加载器开发文档 6.1
	// 跳过 .disabled 后缀的文件（用户手动禁用的 mod）
	if (fileName.endsWith(".disabled")) {
		continue;
	}


================================================================================
第六部分  禁止的注释风格
================================================================================

--------------------------------------------------------------------------------
6.1  禁止无信息量的注释
--------------------------------------------------------------------------------

	反例：

	// 定义变量
	int i = 0;

	// 循环
	for (int j = 0; j < n; j++) {
		// ...
	}

	// 返回结果
	return result;


--------------------------------------------------------------------------------
6.2  禁止复述代码
--------------------------------------------------------------------------------

	反例：

	// 如果 modId 等于 "forge" 返回 FORGE
	if ("forge".equals(modId)) return LoaderTag.FORGE;

	// 应该写成：
	// 文档依据：mod加载器开发文档 6.2
	// modLoader 字段为 "forge" 时判定为 FORGE 加载器
	if ("forge".equals(modId)) return LoaderTag.FORGE;


--------------------------------------------------------------------------------
6.3  禁止 TODO 占位
--------------------------------------------------------------------------------

	反例：

	// TODO: 以后实现
	public void deploy() {
		// ...
	}

	反例：

	// 暂时这样写
	throw new UnsupportedOperationException("未实现");

	正确做法：
		· 没实现的就不写，等实现时再写
		· 不要留占位代码和 TODO


--------------------------------------------------------------------------------
6.4  禁止注释掉的代码
--------------------------------------------------------------------------------

	反例：

	// public void oldMethod() {
	//     // 旧实现
	// }

	正确做法：
		· 删掉
		· 需要保留就交给 Git

--------------------------------------------------------------------------------
7.2  发现文档和代码不一致时
--------------------------------------------------------------------------------

	如果代码实现和文档描述不一致：

		1. 优先相信文档
		2. 检查代码是不是偏离了设计
		3. 如果是代码错了 → 改代码
		4. 如果确实是文档过时 → 改文档 + 记录变更
		5. 绝不能"代码是对的，文档不用改"


================================================================================
第八部分  注释检查清单
================================================================================

每个文件完成后，对照以下清单检查：

	□ 文件头注释存在，包含职责 / 不负责 / 依赖 / 被依赖
	□ 文件头注释包含文档依据
	□ 每个类有类头注释
	□ 每个公开方法有方法头注释
	□ 每个 @throws 有触发条件说明
	□ 复杂逻辑块有注释，说明"为什么"
	□ 硬编码常量有注释，说明来源
	□ 没有复述代码的注释
	□ 没有 TODO 占位
	□ 没有注释掉的代码
	□ 没有无信息量的注释

	以上任意一条不通过 → 不合格，打回重写


================================================================================
第九部分  给 AI 的注释约束（提示词片段）
================================================================================

在投喂任务时，加上这段约束：

【注释要求】
1. 文件头注释必须包含：
   · 一句话职责
   · 文档依据（具体到章节）
   · 职责列表
   · 不负责列表
   · 依赖和被依赖

2. 每个类必须有类头注释，包含文档依据

3. 每个公开方法必须有方法头注释：
   · 一句话说明
   · 文档依据
   · @param / @return / @throws

4. 复杂逻辑块必须有注释，说明"为什么这么做"
   而不是"这里在做什么"

5. 禁止以下注释风格：
   · 复述代码的注释（如 "i 加 1"）
   · 无信息量的注释（如 "定义变量"）
   · TODO 占位
   · 注释掉的代码

6. 每个硬编码常量必须有注释说明来源和依据

7. getter / setter / 简单构造方法 / equals / hashCode 
   不需要注释
